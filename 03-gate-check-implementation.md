# Sentinel: Gate-Check Implementation Prompt (Portable — for any AI coding agent, any project)

**Version 1.0**

This prompt is the one that actually implements — the prior two deliberately stop at "propose and wait for review." Confirm with the user that the proposals have been reviewed and approved before running this, if that hasn't already happened.

---

## The prompt

You are implementing the gate-check proposals from prior audit passes as real, working, automated checks — not proposing new ones from scratch. Ground everything in what actually exists in this project and prior audit output, not in memory of other projects or prior conversations with this user. Where a proposal is unclear, stale, or turns out not to hold up against the current codebase, say so and adjust rather than implementing it blindly just because it was proposed. Any incidental finding you notice along the way that isn't part of implementing the gate check itself still needs a disposition — logged to `sentinel-notes/TODO.md` at minimum — not just a mention that never gets tracked.

**Agent identification.** This prompt works with any AI coding agent capable of reading a codebase, running shell commands, and creating git commits — Claude Code, OpenAI Codex, or similar. If `PROJECT_PROFILE.md` or `AGENTS.md`/`CLAUDE.md` already establishes which agent and which conventions apply, use those rather than re-detecting. Whatever attribution behavior your specific tool has (Claude Code's, for instance, is described below as one concrete example) needs handling the same way regardless of which tool this actually is — check what your own tool does before assuming Claude Code's specific behavior is the only one that matters.

When implementation surfaces a genuine architectural fork you weren't anticipating — a mechanism built for one purpose that could reasonably be extended to cover another, a scoping question the original proposal didn't settle — that's exactly the kind of thing to stop and ask about rather than deciding silently, the same as any other point in this process where you ask the user something.

When you ask the user anything — one of this prompt's own scripted questions or something that comes up along the way — phrase it in plain language a non-specialist could follow. Say what's actually being decided before naming any internal mechanism, rule, or file involved, and make sure each option offered is a complete, actionable choice on its own rather than a fragment of engineering detail. The person commissioned this process; they shouldn't need to already track its internals to answer a question about their own project.

**If there's no real VCS trigger mechanism (or the user doesn't want hooks).** Check whether this project uses git — or a different VCS with its own comparable trigger mechanism, like Perforce's triggers, common in game development specifically — before assuming a `commit-msg`/pre-commit hook is the only option; a non-git VCS with a real trigger mechanism should use that mechanism the same way git hooks are used below, not fall back to the manual-command path just because it isn't git. If there's genuinely no VCS-level trigger available at all, or the user simply prefers not to use hooks, build a standalone manual command instead (a script invocable as `npm run sentinel:check`, `python sentinel_check.py`, `./sentinel-check.sh`, or whatever fits this project's stack) that runs every check in one pass and prints the same actionable output a hook would. This is not a lesser fallback bolted on as an afterthought — treat it as a first-class outcome of Part 2, and make sure the person is told plainly, in the Deliverables summary, that without a hook there's no automatic trigger: they must run this command themselves before considering changes done, since nothing else will remind them. If the project does have a usable trigger mechanism and hooks are wanted, still create the manual command alongside it — it's useful for confirming a check works, and for anyone who wants to run it without committing.

**If some of Sentinel's own output is gitignored, that's a distinct problem from "no VCS" or "no hooks," even though the fix looks similar.** A git hook — `pre-commit`, `commit-msg`, or any other trigger — only ever sees staged or committed content; a gitignored file is never part of a commit's diff, by definition, regardless of whether hooks exist or are wanted at all. If the Design & Code Quality Audit's Part 11 local-vs-shared decision (or any other reason) leaves `AGENTS.md`/`CLAUDE.md`, the design document, or `sentinel-notes/TODO.md` gitignored, no hook-based version of their currency checks can ever work — not "doesn't currently work," structurally cannot, the same way a hook can't react to a file it's never shown. Don't discover this partway through implementing a hook for one of these checks; check which of the file-currency checks in Part 2 below target a gitignored path *before* building anything, and route those specifically to a manual, working-tree-reading script instead — not `git diff --cached`/`git show :<path>`, but a direct read of the file as it currently sits on disk, since there's no staged version to compare against in the first place.

This can combine with the no-VCS/no-hooks case above (build one manual command that covers both reasons at once) or stand alone in a project that has git, uses hooks for everything else, and only needs this working-tree-reading path for the specific checks that target gitignored files — don't assume the two always travel together. If they're handled by one combined script, name the two reasons separately in the Deliverables section below rather than letting "no hook" cover both, since a reader trying to understand why a specific check isn't hook-enforced needs to know which of the two structurally different reasons applies to it.

**If the user doesn't want *any* of Sentinel's output visible in the project at all** (not just local-only, but no trace of gate-check infrastructure in the tracked tree — no `.githooks/`, no `core.hooksPath`, nothing a `git log` or a fresh clone would ever surface), that's a stronger version of "prefers not to use hooks," not a separate case needing its own logic: the same manual-command mechanism applies, just also kept out of version control itself (gitignored alongside whatever else this project already keeps local-only). Confirm this is genuinely what's wanted before defaulting to it, the same as any other Part 0 mechanism choice — an untracked manual command has the same "nothing reminds you to run it" property as any other manual command, plus it won't survive being reconstructed on a fresh clone, so name that tradeoff explicitly when proposing it.

**If this is an update run.** Check `PROJECT_PROFILE.md` for whether this project was already audited under an older version of these prompts. If so, any existing Sentinel-built gate-check hook needs the same re-validation this prompt already requires for newly-built checks (Part 3's adversarial testing standard), not a pass just because Sentinel built it before — a hook built under an older version can carry bugs that were already found and fixed in the current prompt text but never reached the actual file. Treat it the same as re-validating a stale proposal in Part 1: read what it currently does, check it against the current version's requirements (staged-vs-working-tree, real-commit testing, structural-proxy-defeat, tracked hook source), and flag or fix whatever's actually out of date rather than assuming it's still correct. If the Integration Audit flagged a pre-existing *non*-Sentinel system for the same reasons, apply this identical rigor to it too, whether the user wants it converted to Sentinel's conventions or kept in its own style (per the Part 0 question there) — the adversarial testing standard doesn't depend on who originally built the check.


### Scope — Enumerate every surface first

Identify every distinct application surface in this repo by its actual top-level folders/packages (or independent packages in a monorepo), the same way prior audits did. Confirm whether gate checks should be shared across surfaces or implemented per-surface, based on whether the surfaces share the same registries/subsystems (established in the prior audits' Scope sections, if available) or run independently.

### Part 0 — Locate the source material

If `INTEGRATION_CHECKLIST.md` doesn't exist in the project, stop here and tell the user to run the Integration Audit prompt first — don't fabricate a checklist from scratch in this prompt, since re-validating and implementing proposals is a different task from generating them in the first place.

Read, in full:

- `INTEGRATION_CHECKLIST.md` and its gate-check step description (from the Integration Audit's Part 3, deliverable 2)
- `./sentinel-notes/TODO.md` and any `[issue]-design-brief.md` files, specifically the "candidate gate-check items" flagged by the Design & Code Quality Audit
- Any existing `sentinel-exceptions` file, if the exceptions mechanism was already partially set up
- AGENTS.md, for anything relevant to how commits/gating already work in this project
- `PROJECT_PROFILE.md`, if present — reuse its "existing automation" finding instead of re-detecting the project's automation mechanism from scratch in the step below; only re-check if it looks stale or absent

Also identify what automation mechanism this project already uses (native git hooks, husky, pre-commit framework, a CI pipeline config, npm/package scripts) rather than introducing a second, competing system — the new checks should slot into whatever's already there. Confirm first whether this project uses git at all — if not, or if the person prefers not to use hooks, the manual-command approach described above is the mechanism, not a fallback to apologize for. If nothing exists yet and git is in use, propose the simplest hook-based mechanism that fits this project's stack, say why, and get the user's confirmation on that choice specifically before building anything — don't fold this into the broader Part 1 confirmation as an assumed given, since there may genuinely be more than one reasonable option for a given stack and the choice is easy to make silently otherwise.

Apply whichever style-matching answer was recorded in the Integration Audit's Part 0: if the user chose to match an existing system's conventions, name new files, exceptions mechanisms, and commit trailers in that system's naming/format style rather than Sentinel's own (`sentinel-exceptions.json`, `Sentinel-Override`) — the underlying mechanics (structural bullet checks, staged-content reading, exit codes) stay the same regardless of style, only the naming and surface conventions adapt. If they chose Sentinel's own conventions, or no pre-existing system was found, use Sentinel's defaults as already described throughout this prompt.

If native git hooks are the mechanism, remember that `.git/hooks/` is never tracked by git itself — nothing in it survives a fresh clone, a reinstall, or being recreated on another machine. Dropping the hook script directly into `.git/hooks/commit-msg` with no other trace of it in the repository means the enforcement can silently stop existing with no error and no warning, which looks identical from the outside to "the check has a bug" but is a completely different failure. Keep the actual hook source in a tracked location in the repository (e.g. a `.githooks/` or `sentinel-gate/hooks/` directory that gets committed), and either set `git config core.hooksPath` to point at it, or provide and document a simple install step that copies it into `.git/hooks/` and marks it executable. State in the Deliverables summary where the tracked source lives and how it gets installed — this is exactly the kind of thing a future clone or session needs to know and currently has no way to discover on its own.

### Part 1 — Re-validate every proposal against the current codebase

Time has passed since the proposals were written, and code may have changed. For every proposed gate-check item, re-check it against the actual current state of the codebase — across all directories/surfaces identified in Scope — before implementing it:

- Does the pattern/touchpoint the proposal describes still exist as described?
- Would implementing the check exactly as originally proposed produce false positives or false negatives against the codebase as it stands right now?
- Has anything changed (a refactor, a new pattern introduced since the audit) that makes the proposal stale, wrong, or in need of adjustment?

Update or correct each proposal as needed before moving to implementation. Note any proposal you're deliberately not implementing and why (too vague to make mechanical, no longer applicable, superseded by something else found in this re-check).

Before proceeding to Part 2, present the re-validated list to the user and get explicit confirmation for anything that changed from its originally proposed form — an adjusted, deferred, or dropped item was not what the user actually approved when they reviewed `INTEGRATION_CHECKLIST.md`, so implementing it without a fresh confirmation would silently bypass their review. Items that came through re-validation unchanged don't need re-asking; only the deltas do.

### Part 2 — Implement

For each validated and confirmed proposal, write the actual check using the automation mechanism identified in Part 0.

Every check must:

- Run automatically before commit if a hook is the mechanism, or be invocable as a single manual command if it isn't (see the no-git note above) — either way, not something scattered across multiple steps someone has to remember to run
- If the manual command exists because the project genuinely had no VCS at the time `03` ran (not because the user preferred no hooks, or because some checks target gitignored files per the note above), have it check for a `.git` directory on every invocation, not just once at build time. A no-VCS project can gain git at any point after this prompt finishes, and nothing else would ever notice. If `.git` now exists where it didn't before, print one clear, low-friction offer — "This project now has git. Want to switch these checks to run automatically via a pre-commit hook instead of manually?" — and, if the user says yes, do the actual Part 0/Part 2 hook setup (tracked hook source, `core.hooksPath` or an install step, all of it) rather than just noting the offer was made. Say no once and the script should stop asking every single run — track that decision (a marker file, a line in `AGENTS.md`) rather than re-prompting on every invocation, which would just teach the user to dismiss it unread. This check does not apply to a manual command built for either of the other two reasons (hooks unwanted, or a specific file gitignored) — those preferences don't change just because git now exists, and re-offering hooks there would be re-litigating a decision the user already made deliberately, not surfacing a new option.
- Only gate the diff of the commit (or, for the manual command with no commit boundary, the diff against the last time it was run, or the whole working tree if that's clearer for this project) — not the entire codebase's pre-existing state; a newly implemented check should not suddenly block on violations that already existed before this check existed
- Output actionable violations in the established format: the specific rule/category violated, the exact file (and line, where the check is diff/grep-based), and the required correction
- Respect the exceptions mechanism — read the exceptions file if one is designed/exists, honor unexpired entries, fail exactly as if no exception existed once an entry's review-by date has passed
- Apply per-surface correctly, per the Scope determination (one shared check, or one instance per surface, as appropriate)
- Read from the git staging area (the index) for any check that inspects file content, not the raw working tree — a naive implementation that reads files directly off disk will check whatever happens to be there, which may include unstaged edits that were never part of the commit being checked. Use `git diff --cached` / `git show :<path>` (or the equivalent in whatever language the check is written in) to inspect what's actually staged, not `fs.readFileSync` or similar direct file reads. This distinction is easy to get wrong and easy to leave unverified — treat "does the hook check staged content specifically" as a fact to confirm, not an assumption to leave open, before considering any git-hook-based check done.
- Also be invocable as a full-repo scan, not just diff-scoped, via a separate mode of the same manual command built for the no-git case — e.g. `sentinel-check --full` alongside the default diff-scoped `sentinel-check`. This catches drift the incremental hook structurally cannot: violations from git history predating these checks, manual edits outside a commit, or an interaction effect between two separately-committed changes that each passed on its own. Don't run this on every commit — it's meaningfully slower, and paying that cost per commit either discourages small commits or trains people to bypass the hook. Wire it into a CI-scheduled job (nightly/weekly) if the project has CI, or a `pre-push` hook otherwise; prefer CI-scheduled when both are available. State the chosen cadence in the Deliverables summary — an untriggered full-scan mode protects nothing.
- The full-scan mode must actually enforce, not just report — a non-zero exit code or failed CI job on violations, held to the same actionable-output standard as the diff-scoped check. A script that only logs findings without failing its trigger isn't a gate. If a report-only version already exists in the codebase (built earlier as a standalone diagnostic), don't treat wiring it in as-is as satisfying this — check whether it actually sets an exit code, and add real blocking behavior (or a thin wrapper that translates its findings into one) if it doesn't.
- A full-repo scan surfaces the entire accumulated backlog from Part 4 on its first run, not just new violations — blocking on 100% of it immediately would reproduce the same "newly implemented check suddenly blocks on pre-existing violations" problem the diff-scoping rule above exists to prevent, just at repo-wide scope. Handle it the same way: treat the Part 4 report-only pass as the baseline, and block only on violations that weren't already in it. Anything in the baseline stays a tracked backlog item until fixed or exempted with an owner and review-by date — don't let an existing backlog become a permanent excuse for leaving the full-scan mode toothless.
- If native git hooks are part of the mechanism, the full-scan mode should also verify its own enforcement infrastructure is intact — the hook files exist at the correct path, are executable, and haven't been silently reverted (a real risk given `.git/hooks/` isn't tracked, per the Part 0 note). A missing or broken hook is itself the kind of drift a periodic scan exists to catch — fail the full scan if the expected hook isn't there.

If a design document exists (per Part 2's design-doc gate), its content accuracy needs a separate mechanism, not folded into the full-scan mode — verifying `DESIGN.md` still says something true requires reasoning about whether it matches the codebase, closer to re-running part of the design audit than a linter pass, and bolting that onto the same frequent trigger as the mechanical checks would make the full-scan mode slow for a benefit that doesn't need checking that often. Trigger this off releases if the project has a clear rhythm (a tag, a version bump, a changelog entry), with a calendar fallback (quarterly is a reasonable default, confirm with the user) for projects without one — the same two-tier pattern as the full-scan mode's own cadence choice. Make this a prompt, not a block — whether `DESIGN.md` still matches reality is a judgment call once flagged, not something to hard-block a release over. State in the Deliverables summary what triggers this and how it surfaces.

Common blind spots to check for and avoid in every check you write, regardless of what it's checking:

- Justify every file/path exclusion (skip-list, allowlist) per rule, not per file. A reason to exclude a file from one rule a script enforces does not automatically justify excluding it from every other rule the same script enforces — e.g. a definitions file (like a central CSS variables file) legitimately repeats values and should be excluded from a duplication check, but it can still *reference* an undefined value inside its own rules and must NOT be excluded from a usage-validity check just because it was excluded from the duplication one. Before finalizing any exclusion, write out which specific rule it's exempting and confirm the file genuinely can't violate that specific rule — not just that it seemed reasonable to skip generally.
- Don't assume a file only ever plays one role. The exclusion problem above generalizes: any file that both *defines* something and *uses/references* something (an index file that both exports and re-exports, a config file that sets defaults and reads other settings, a schema file that both declares and derives) can violate a rule from either role — check both, don't exempt the file just because its primary role seems safe.
- Check deletions, not just additions. A check that only scans added lines will miss a violation introduced by removing something protective — a null check, a sanitizer call, a bounds check, an early-return guard. If the rule is about a protection existing, verify the diff didn't remove it, not just that it didn't add a bad pattern.
- Resolve cross-file references against the whole codebase, not just the changed file. Anything with a "this name refers to something defined elsewhere" shape (a variable, an import, a translation key, a config key, a route name, a database column) needs its check to look at the actual current source of truth for that name, not just pattern-match within the diff's own file.
- Fail loudly, never silently, when the check itself can't run. A parse error, a missing file, a failed tool invocation, or a caught exception must fail the check (or at minimum flag "unable to verify" as its own distinct outcome) — never let error-handling that swallows a failure quietly resolve to a pass. Audit for patterns like a shell `|| true` or a bare `except: pass` sitting between the check's logic and its final exit code.
- Don't let performance shortcuts correlate with risk. If a check samples, truncates, or skips very large diffs for speed, that's exactly backwards — large, complex changes are statistically the ones most likely to hide the problem the check exists to catch, not the ones safe to skip.
- Prefer patterns over enumerated file lists. A check hardcoded to a fixed list of watched files/directories silently stops covering anything added later. Where the touchpoint inventory names a *kind* of file (all component definitions, all route handlers, all translation files), write the check against that pattern, not a snapshot of today's file list.
- Translate every vague adjective into a concrete, testable number before implementing. A proposal or existing instruction phrased as "brief," "short," "single-sentence," or "concise" is not yet implementable — you (or a future session) will drift back to whatever "brief" means to you that day, the same way natural-language instructions against co-author trailers proved unreliable. Pick an explicit numeric threshold (a character or line-count cap is the usual fit for text conventions) and enforce that instead. For commit message conventions specifically, a reasonable default absent other guidance: subject line capped around 50-72 characters, body bullets capped around 72-80 characters — but confirm the exact numbers fit how this project's user actually wants to read their own commit log, rather than assuming the default is right for them.
- A numeric cap is necessary but not sufficient when the rule you're actually enforcing is structural, not just about size. Capping line length is meant as a proxy for "a few bullets, not a narrative" — but it's a satisfiable proxy: several short, unmarked lines can reconstruct the exact narrative-paragraph shape the rule exists to prevent, just wrapped to fit under the cap. Where the underlying rule implies a structural form (a bullet list rather than prose), the length cap alone doesn't encode that — also require an explicit structural signal that's actually checkable (each body line must start with a real bullet marker like `- `) and a cap on the number of such lines (not just their individual length), since a marker on every line of an otherwise-long list is just as much a disguised narrative as unmarked wrapped prose is.

Implement the commit-convention checks as a `commit-msg` hook where git is in use, mechanically enforcing rather than merely instructing. The specific structural rules below (bullet markers, wrap limits, the narrative-body hard block) apply only if the style chosen in the Integration Audit's Part 4 is bullet-based (terse-with-bullets, or Conventional Commits with a bullet body) — if the user explicitly chose detailed narrative descriptions as their preferred style, do not build these structural checks at all; enforcing "bullets, not prose" against someone who deliberately asked for prose would override their own stated preference, not protect it. For a narrative-style project, enforce only the hygiene rules that apply regardless of style (subject line format, attribution stripping, no co-author notes) plus a generous sanity ceiling on total body length to catch genuinely runaway messages, not a bullet/paragraph-count structure that contradicts the style itself. For a custom convention, build the hook around whatever that convention actually specifies rather than defaulting to the bullet-based rules below.

For bullet-based styles specifically: subject line is a single line with no wrapping, capped at the character limit settled on above; a commit with nothing more to say has no body at all. Beyond that:

- Every logical bullet must start with a real bullet marker (e.g. `- `) — not just be short enough to pass a length check — and the number of *logical bullets* (not raw physical lines) is capped at a small count (5 is a reasonable default, confirm with the user).
- A bullet may wrap onto one indented continuation line with no marker if its content doesn't fit on one line — up to 2 physical lines per bullet (confirmed with the user at 2), not more. The continuation line must be visually indented so it's structurally distinguishable from a new bullet, and the bullet's combined length across both lines is capped at roughly double the single-line limit (e.g. ~160 characters if the single-line cap is 80) — not just each physical line individually. This combined ceiling matters as much as the per-line one: without it, wrapping becomes a loophole for cramming two maximally-stuffed lines into what's still functionally a mini-paragraph. A length cap alone is not this requirement fully implemented — see the numeric-cap blind spot noted in Part 2.
- The bullet-count cap stays a hard block by default. Don't soften it to a non-blocking warning just because it sometimes reflects a legitimate judgment call (a commit that's genuinely one large coherent unit of work) — per the exceptions discussion in the Integration Audit's Part 5, the right way to handle that is a required, reasoned override (a `Sentinel-Override: <reason>` trailer the person deliberately writes), not a warning that erodes the way unenforced instructions already have elsewhere in this project.
- When the cap is exceeded and no override is present, the failure message should lead with "does this commit bundle together several separate things? consider splitting it" — per the granularity preference from the Integration Audit's Part 4 — before mentioning the override option. Never suggest moving displaced detail into a code comment, a separate document, or conversation only — that defeats the point of the commit message, since the Integration Audit later mines commit history for real touchpoints. If a change genuinely is one coherent unit that touches many things, describing it at a higher level with fewer, broader bullets is usually the right fix; if it genuinely can't be, that's what the override is for.
- The multi-paragraph narrative check (the blank-line/structure violation, not the bullet count) stays a true hard block with no override available for bullet-based projects — there's no legitimate case where a bullet-style commit body should read as prose.

None of this paragraph applies to a project that chose narrative style, per the note above.

Regardless of style: any co-author note or auto-generated attribution/session-link trailer your specific tool might add (Claude Code, for example, can add a "Generated with Claude Code" line and a `Claude-Session:` trailer unless suppressed) is stripped or the commit is rejected outright. Where there's no git (or no hook), these specific commit-message checks have no equivalent to enforce — a manual command has no commit message to inspect — so skip them there rather than inventing a strained analog; the AGENTS.md-touched, README-touched, design-doc-touched (if applicable), and TODO-sync checks below still apply regardless, since those are about the code changes themselves, not the commit metadata. Treat instructing yourself not to add these as insufficient on its own — a tool's own settings-level attribution controls are documented as unreliable for Claude Code and shouldn't be assumed reliable for any other tool either, so the hook itself is the enforcement, not a suggestion you're trusted to follow. Also implement the AGENTS.md-touched, README-touched, design-doc-touched (if a design document exists), and TODO-sync checks as real enforced checks here, not just descriptions — remember AGENTS.md is the highest-priority of these per the Integration Audit's Part 2, since it's the authoritative record future sessions rely on, and the design-doc check should use the narrower "architecturally significant" trigger described there rather than the same bar as the other two. Build the TODO-sync check's brief-linked half as a real hard check (a commit modifying `sentinel-notes/[issue]-design-brief.md` without a corresponding status change in `TODO.md` is a concrete, structural signal, not a guess) and its unlinked-item half as a non-blocking reminder, exactly as scoped in Part 2 — don't try to force a hard check onto the half of this that has no reliable signal to check against.

### Part 3 — Test each check

For every newly implemented check, verify it actually works: deliberately construct a violation (a throwaway change, a scratch commit you can discard, or a dry-run/lint-only invocation if the mechanism supports one) and confirm the check fires with the correct actionable message. Then confirm a compliant change passes cleanly with no false positive.

For any check wired as a native git hook specifically, a dry-run/lint-only invocation of the check's own logic does not satisfy this — it proves the logic works, not that the hook file exists at the exact path and filename git expects, is executable, and is something git will actually invoke. Those are different failures that look identical from the outside (an obviously bad commit sails through with no resistance), so the mandatory test for a git-hook-based check is a real `git commit` attempt with a scratch/throwaway change, discarded afterward — not a substitute invocation of the check script directly. Before that, as a first, trivial sanity check that costs almost nothing: attempt to commit something blatantly, maximally non-compliant — a single-line message far over any reasonable length, zero effort at the required structure — and confirm it's rejected. If even this trivial case passes, the hook isn't wired correctly at all, and there's no point testing subtler edge cases until that's fixed.

For any check wired as a native git hook specifically, also confirm it reads staged content, not the working tree — stage a compliant version of a file while leaving a different, non-compliant version sitting unstaged on disk, and confirm the hook evaluates the staged version, not what's currently on disk. If it evaluates the working tree instead, the hook can pass or fail a commit based on content that was never actually part of it — a real correctness bug, not a minor implementation detail, and not something to leave as an open question at the point where you're about to trust the hook.

For any check whose numeric cap is a proxy for a structural rule (a length limit standing in for "bullets, not narrative"; a count limit standing in for "a few items, not many"), specifically test whether the cap can be satisfied while still recreating the exact structure it's meant to prevent — e.g. a multi-paragraph commit body wrapped so no individual line exceeds the character cap, with no bullet markers at all. If that passes, the check only enforces the number, not the rule the number was supposed to approximate, and needs the structural signal (a required marker, a count limit) added before it ships. Also test the specific case of several short, unmarked, declarative sentences forming one continuous block with no blank-line paragraph break and staying under any count cap — a rule that only detects narrative by counting blank-line-separated blocks (rather than requiring an actual bullet marker on every line) will miss exactly this shape, since it's technically one block, not several.

If bullet wrapping is part of this project's convention (a bullet allowed to span an indented continuation line), test all three edges of it directly: a legitimately wrapped 2-line bullet within the combined length ceiling passes; a continuation line that isn't indented is correctly treated as a new (unmarked, thus invalid) bullet rather than accepted as a continuation; and a bullet attempting a third line, or exceeding the combined character ceiling across its two lines, is rejected rather than silently allowed just because each individual physical line stays under the single-line cap. That third case is the same "numeric cap satisfiable without enforcing the structure" failure as above, just recurring one level down — the wrap allowance is itself a rule with a proxy-able cap, and it needs the same adversarial scrutiny the original bullet-count rule got.

Before enabling any new check as blocking, run it against a reasonable sample of real historical data relevant to what it checks — past commits for a commit-convention check, existing files for a content check — to confirm it doesn't reject things that were already legitimate. Synthetic violation and compliance tests catch conceptual gaps, but they can't catch a rule that's technically sound yet would have blocked a chunk of the project's own real, acceptable past work; that only shows up against real data, and it's worth doing before flipping the check from advisory to blocking, not after.

For any check that has a file/path exclusion, this is not enough — also construct an adversarial test specifically inside the excluded file: a violation of the check's actual rule, placed in the file the check skips, and confirm honestly whether the check catches it or not. If it doesn't, the exclusion is wrong (see Part 2) and needs narrowing before this check ships, not a note to fix later — a check with a known, un-narrowed blind spot in the exact file most likely to need it is worse than not having the check, since it creates false confidence. More generally: don't stop at the happy-path violation test for any check — think about what a change could look like that satisfies the letter of the check's logic while still doing the thing the check exists to prevent, and test that too. This includes testing each of the code-agnostic gaps from Part 2 where relevant to the specific check: does it catch a violation introduced via deletion, not just addition; does it correctly resolve a cross-file reference rather than only pattern-matching within the diff; does it catch a violation in a file playing its secondary/using role, not just the primary/defining role you tested first; does a large/complex synthetic diff still get fully checked rather than shortcut; does a forced tool failure inside the check surface as a failure rather than a silent pass.

Note any check you couldn't safely live-test and explain why, rather than silently skipping verification.
