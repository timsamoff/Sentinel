# Sentinel: Gate-Check Implementation Prompt (Portable — for any AI coding agent, any project)

This prompt is the one that actually implements — the prior two deliberately stop at "propose and wait for review." Confirm with the user that the proposals have been reviewed and approved before running this, if that hasn't already happened.

---

## The prompt

You are implementing the gate-check proposals from prior audit passes as real, working, automated checks — not proposing new ones from scratch. Where a proposal is unclear, stale, or turns out not to hold up against the current codebase, say so and adjust rather than implementing it blindly just because it was proposed.

**Agent identification.** This prompt works with any AI coding agent capable of reading a codebase, running shell commands, and creating git commits — Claude Code, OpenAI Codex, or similar. If `PROJECT_PROFILE.md` or `AGENTS.md`/`CLAUDE.md` already establishes which agent and which conventions apply, use those rather than re-detecting. Whatever attribution behavior your specific tool has (Claude Code's, for instance, is described below as one concrete example) needs handling the same way regardless of which tool this actually is — check what your own tool does before assuming Claude Code's specific behavior is the only one that matters.

When implementation surfaces a genuine architectural fork you weren't anticipating — a mechanism built for one purpose that could reasonably be extended to cover another, a scoping question the original proposal didn't settle — that's exactly the kind of thing to stop and ask about rather than deciding silently. When you do, phrase it in plain language a non-specialist could follow: say what's actually being decided, and why it matters, before naming the specific rule ID, file, or internal mechanism involved. Each option offered should read as a complete, actionable choice a person could act on without needing to already track the codebase's internals — not an engineering summary of the fork itself.

**If there's no git (or the user doesn't want hooks).** Check whether this project actually uses git before assuming a `commit-msg`/pre-commit hook is the right mechanism. If it doesn't — no VCS at all, a different VCS, or the user simply prefers not to use hooks — build a standalone manual command instead (a script invocable as `npm run sentinel:check`, `python sentinel_check.py`, `./sentinel-check.sh`, or whatever fits this project's stack) that runs every check in one pass and prints the same actionable output a hook would. This is not a lesser fallback bolted on as an afterthought — treat it as a first-class outcome of Part 2, and make sure the person is told plainly, in the Deliverables summary, that without a hook there's no automatic trigger: they must run this command themselves before considering changes done, since nothing else will remind them. If the project does use git and hooks are wanted, still create the manual command alongside the hook — it's useful for confirming a check works, and for anyone who wants to run it without committing.


### Scope — Enumerate every surface first

Identify every distinct application surface in this repo by its actual top-level folders/packages (or independent packages in a monorepo), the same way prior audits did. Confirm whether gate checks should be shared across surfaces or implemented per-surface, based on whether the surfaces share the same registries/subsystems (established in the prior audits' Scope sections, if available) or run independently.

### Part 0 — Locate the source material

If `INTEGRATION_CHECKLIST.md` doesn't exist in the project, stop here and tell the user to run the Integration Audit prompt first — don't fabricate a checklist from scratch in this prompt, since re-validating and implementing proposals is a different task from generating them in the first place.

Read, in full:

- `INTEGRATION_CHECKLIST.md` and its gate-check step description (from the Integration Audit's Part 3, deliverable 2)
- `./sentinel-notes/TODO.md` and any `[issue]-design-brief.md` files, specifically the "candidate gate-check items" flagged by the Design & Code Quality Audit
- Any existing `sentinel-exceptions` file, if the exceptions mechanism was already partially set up
- AGENTS.md, for anything relevant to how commits/gating already work in this project
- `PROJECT_PROFILE.md`, if present — reuse its "existing automation" finding instead of re-detecting the project's automation mechanism from scratch in the step below; only re-check if it looks stale or absent

Also identify what automation mechanism this project already uses (native git hooks, husky, pre-commit framework, a CI pipeline config, npm/package scripts) rather than introducing a second, competing system — the new checks should slot into whatever's already there. Confirm first whether this project uses git at all — if not, or if the person prefers not to use hooks, the manual-command approach described above is the mechanism, not a fallback to apologize for. If nothing exists yet and git is in use, propose the simplest hook-based mechanism that fits this project's stack and say why.

If native git hooks are the mechanism, remember that `.git/hooks/` is never tracked by git itself — nothing in it survives a fresh clone, a reinstall, or being recreated on another machine. Dropping the hook script directly into `.git/hooks/commit-msg` with no other trace of it in the repository means the enforcement can silently stop existing with no error and no warning, which looks identical from the outside to "the check has a bug" but is a completely different failure. Keep the actual hook source in a tracked location in the repository (e.g. a `.githooks/` or `sentinel-gate/hooks/` directory that gets committed), and either set `git config core.hooksPath` to point at it, or provide and document a simple install step that copies it into `.git/hooks/` and marks it executable. State in the Deliverables summary where the tracked source lives and how it gets installed — this is exactly the kind of thing a future clone or session needs to know and currently has no way to discover on its own.

### Part 1 — Re-validate every proposal against the current codebase

Time has passed since the proposals were written, and code may have changed. For every proposed gate-check item, re-check it against the actual current state of the codebase — across all directories/surfaces identified in Scope — before implementing it:

- Does the pattern/touchpoint the proposal describes still exist as described?
- Would implementing the check exactly as originally proposed produce false positives or false negatives against the codebase as it stands right now?
- Has anything changed (a refactor, a new pattern introduced since the audit) that makes the proposal stale, wrong, or in need of adjustment?

Update or correct each proposal as needed before moving to implementation. Note any proposal you're deliberately not implementing and why (too vague to make mechanical, no longer applicable, superseded by something else found in this re-check).

Before proceeding to Part 2, present the re-validated list to the user and get explicit confirmation for anything that changed from its originally proposed form — an adjusted, deferred, or dropped item was not what the user actually approved when they reviewed `INTEGRATION_CHECKLIST.md`, so implementing it without a fresh confirmation would silently bypass their review. Items that came through re-validation unchanged don't need re-asking; only the deltas do.

### Part 2 — Implement

For each validated and confirmed proposal, write the actual check using the automation mechanism identified in Part 0.

Every check must:

- Run automatically before commit if a hook is the mechanism, or be invocable as a single manual command if it isn't (see the no-git note above) — either way, not something scattered across multiple steps someone has to remember to run
- Only gate the diff of the commit (or, for the manual command with no commit boundary, the diff against the last time it was run, or the whole working tree if that's clearer for this project) — not the entire codebase's pre-existing state; a newly implemented check should not suddenly block on violations that already existed before this check existed
- Output actionable violations in the established format: the specific rule/category violated, the exact file (and line, where the check is diff/grep-based), and the required correction
- Respect the exceptions mechanism — read the exceptions file if one is designed/exists, honor unexpired entries, fail exactly as if no exception existed once an entry's review-by date has passed
- Apply per-surface correctly, per the Scope determination (one shared check, or one instance per surface, as appropriate)
- Read from the git staging area (the index) for any check that inspects file content, not the raw working tree — a naive implementation that reads files directly off disk will check whatever happens to be there, which may include unstaged edits that were never part of the commit being checked. Use `git diff --cached` / `git show :<path>` (or the equivalent in whatever language the check is written in) to inspect what's actually staged, not `fs.readFileSync` or similar direct file reads. This distinction is easy to get wrong and easy to leave unverified — treat "does the hook check staged content specifically" as a fact to confirm, not an assumption to leave open, before considering any git-hook-based check done.
- Also be invocable as a full-repo scan, not just diff-scoped, via a separate mode of the same manual command built for the no-git case — e.g. `sentinel-check --full` alongside the default diff-scoped `sentinel-check`. This is what catches drift the incremental hook structurally cannot: violations from git history predating any of these checks, manual edits made outside a commit, or an interaction effect between two separately-committed changes that each individually passed their own check. Do not run this on every commit alongside the diff-scoped check — a full scan is meaningfully slower, and paying that cost on every commit either discourages small, frequent commits or trains people to bypass the hook, both of which defeat the point. Instead: if the project has CI, wire the full scan into a scheduled job (nightly or weekly) so it never touches local dev flow at all; if it doesn't, wire it into a `pre-push` hook instead, since push happens far less often than individual commits and is a much less costly moment to spend the extra time. Prefer CI-scheduled over pre-push when both are available. State the chosen cadence explicitly in the Deliverables summary — a full-scan mode that exists but nothing ever triggers protects nothing.
- The full-scan mode must actually enforce, not just report. If it's wired into a CI job or a `pre-push` hook, it must produce a real failure there — a non-zero exit code, a failed CI job — when it finds violations, held to the same actionable-output standard as the diff-scoped check. A script that only logs or prints findings without ever failing the trigger it's wired into is not a gate, regardless of where it's invoked from. If a report-only version of this kind of scan already exists in the codebase (built earlier as a standalone diagnostic tool, before this gate-check pass), don't treat wiring it in as-is as satisfying this requirement — either add real blocking behavior to it directly, or build the gate as a thin wrapper that runs it and translates its findings into a failing exit code. Check for exactly this before assuming an existing full-repo script already does the job: read whether it actually sets an exit code and search for any comment or naming indicating it was deliberately built report-only.
- Because a full-repo scan surfaces the entire accumulated backlog from Part 4 on its very first run, not just new violations, making it block on 100% of that backlog immediately would reproduce the same "newly implemented check suddenly blocks on pre-existing violations" problem the diff-scoping requirement above exists to prevent — just at repo-wide scope instead of per-commit scope. Handle it the same way: treat the Part 4 report-only pass as the baseline snapshot, and have the full-scan mode block only on violations that didn't already appear in that baseline. Anything in the baseline stays a tracked backlog item (per Part 4) until it's either fixed or routed through the exceptions mechanism with an owner and review-by date — never let "we already had a backlog" become a permanent excuse for leaving the full-scan mode toothless indefinitely; the backlog is meant to shrink over time, not to justify never enforcing against it.
- If native git hooks are part of the mechanism, the full-scan mode should also verify its own enforcement infrastructure is still intact — the hook files exist at the correct path, are still executable, and haven't been silently reverted or lost (the natural risk given `.git/hooks/` isn't tracked, per the note in Part 0). A missing or broken hook is itself exactly the kind of drift a periodic scan exists to catch, not just content violations in the code — fail the full scan if the expected hook isn't there rather than only checking for violations the hook was supposed to be preventing.

If a design document exists (per Part 2's design-doc gate above), its content accuracy needs a separate mechanism from everything above — not folded into the full-scan mode. Everything the full-scan mode checks is fast and mechanical (a line length, a token's existence, whether a file was touched); actually verifying that `DESIGN.md` still says something true requires re-reading the document and reasoning about whether it matches the codebase, which is closer to re-running part of the design audit than to a linter pass. Bolting that onto the same frequent trigger as the mechanical checks would make the full-scan mode itself slow for a benefit that doesn't need checking that often. Instead: trigger this re-verification off releases if the project has a clear release rhythm (a git tag, a version bump, a changelog entry — whatever this project actually uses), with a fixed calendar fallback (quarterly is a reasonable default, confirm with the user) for projects that don't tag releases or go long stretches between them — the same two-tier pattern as the full-scan mode's own CI-schedule-or-pre-push choice. Make this a prompt, not a block: unlike the mechanical gates, whether `DESIGN.md` still matches reality is a judgment call once flagged, so hard-blocking a release over it would be the wrong kind of enforcement for something this qualitative. State in the Deliverables summary what triggers this and how it surfaces (an issue, a TODO item, a direct prompt) — the same "state it plainly or it protects nothing" standard as the full-scan mode's own cadence.

Common blind spots to check for and avoid in every check you write, regardless of what it's checking:

- Justify every file/path exclusion (skip-list, allowlist) per rule, not per file. A reason to exclude a file from one rule a script enforces does not automatically justify excluding it from every other rule the same script enforces — e.g. a definitions file (like a central CSS variables file) legitimately repeats values and should be excluded from a duplication check, but it can still *reference* an undefined value inside its own rules and must NOT be excluded from a usage-validity check just because it was excluded from the duplication one. Before finalizing any exclusion, write out which specific rule it's exempting and confirm the file genuinely can't violate that specific rule — not just that it seemed reasonable to skip generally.
- Don't assume a file only ever plays one role. The exclusion problem above generalizes: any file that both *defines* something and *uses/references* something (an index file that both exports and re-exports, a config file that sets defaults and reads other settings, a schema file that both declares and derives) can violate a rule from either role — check both, don't exempt the file just because its primary role seems safe.
- Check deletions, not just additions. A check that only scans added lines will miss a violation introduced by removing something protective — a null check, a sanitizer call, a bounds check, an early-return guard. If the rule is about a protection existing, verify the diff didn't remove it, not just that it didn't add a bad pattern.
- Resolve cross-file references against the whole codebase, not just the changed file. Anything with a "this name refers to something defined elsewhere" shape (a variable, an import, a translation key, a config key, a route name, a database column) needs its check to look at the actual current source of truth for that name, not just pattern-match within the diff's own file.
- Fail loudly, never silently, when the check itself can't run. A parse error, a missing file, a failed tool invocation, or a caught exception must fail the check (or at minimum flag "unable to verify" as its own distinct outcome) — never let error-handling that swallows a failure quietly resolve to a pass. Audit for patterns like a shell `|| true` or a bare `except: pass` sitting between the check's logic and its final exit code.
- Don't let performance shortcuts correlate with risk. If a check samples, truncates, or skips very large diffs for speed, that's exactly backwards — large, complex changes are statistically the ones most likely to hide the problem the check exists to catch, not the ones safe to skip.
- Prefer patterns over enumerated file lists. A check hardcoded to a fixed list of watched files/directories silently stops covering anything added later. Where the touchpoint inventory names a *kind* of file (all component definitions, all route handlers, all translation files), write the check against that pattern, not a snapshot of today's file list.
- Translate every vague adjective into a concrete, testable number before implementing. A proposal or existing instruction phrased as "brief," "short," "single-sentence," or "concise" is not yet implementable — you (or a future session) will drift back to whatever "brief" means to you that day, the same way natural-language instructions against co-author trailers proved unreliable. Pick an explicit numeric threshold (a character or line-count cap is the usual fit for text conventions) and enforce that instead. For commit message conventions specifically, a reasonable default absent other guidance: subject line capped around 50-72 characters, body bullets capped around 72-80 characters — but confirm the exact numbers fit how this project's user actually wants to read their own commit log, rather than assuming the default is right for them.
- A numeric cap is necessary but not sufficient when the rule you're actually enforcing is structural, not just about size. Capping line length is meant as a proxy for "a few bullets, not a narrative" — but it's a satisfiable proxy: several short, unmarked lines can reconstruct the exact narrative-paragraph shape the rule exists to prevent, just wrapped to fit under the cap. Where the underlying rule implies a structural form (a bullet list rather than prose), the length cap alone doesn't encode that — also require an explicit structural signal that's actually checkable (each body line must start with a real bullet marker like `- `) and a cap on the number of such lines (not just their individual length), since a marker on every line of an otherwise-long list is just as much a disguised narrative as unmarked wrapped prose is.

Implement the commit-convention checks as a `commit-msg` hook where git is in use, mechanically enforcing rather than merely instructing: subject line is a single line with no wrapping, capped at the character limit settled on above; a commit with nothing more to say has no body at all; if a body exists, every line must start with a real bullet marker (e.g. `- `) — not just be short enough to pass a length check — and the number of body lines is capped at a small count (5 is a reasonable default, confirm with the user), each individually capped at the body character limit settled on above. A length cap by itself is not this requirement fully implemented — see the blind-spot note in Part 2 above about numeric caps being satisfiable without enforcing the structure they're meant to proxy for. The bullet-count cap stays a hard block by default — do not soften it to a non-blocking warning just because it sometimes reflects a legitimate judgment call (a commit that's genuinely one large coherent unit of work) rather than a pure formatting violation; per the exceptions discussion in the Integration Audit's Part 5, the right way to handle that legitimate case is a required, reasoned override — a commit trailer such as `Sentinel-Override: <reason>` that the person deliberately writes — not a warning that can be ignored and erodes the same way unenforced instructions already have elsewhere in this project. When the cap is exceeded and no override trailer is present, the hook's failure message should lead with "does this commit bundle together several separate things? consider splitting it into multiple commits" — per the granularity preference already established in the Integration Audit's Part 4 — before it mentions the override option at all. Do not suggest, in that message or anywhere else, moving the displaced detail into a code comment, a separate document, or leaving it only in conversation — that solves the cap at the cost of the actual point of a commit message, since the Integration Audit later mines commit history for real touchpoints, and information about what changed and why needs to live there, not be scattered somewhere the audit trail can't see it. If a change genuinely is one coherent unit of work that happens to touch many things, the right fix is usually describing it at a higher level with fewer, broader bullets, not exhaustively listing every touched file — but if it genuinely can't be, that's exactly what the override trailer is for. The multi-paragraph narrative check (the blank-line/structure violation, not the bullet count) should stay a true hard block with no override available — there's no legitimate case where a commit body should read as prose, so unlike the bullet-count cap, this one doesn't need an escape hatch. Any co-author note or auto-generated attribution/session-link trailer your specific tool might add (Claude Code, for example, can add a "Generated with Claude Code" line and a `Claude-Session:` trailer unless suppressed) is stripped or the commit is rejected outright. Where there's no git (or no hook), these specific commit-message checks have no equivalent to enforce — a manual command has no commit message to inspect — so skip them there rather than inventing a strained analog; the AGENTS.md-touched, README-touched, design-doc-touched (if applicable), and TODO-sync checks below still apply regardless, since those are about the code changes themselves, not the commit metadata. Treat instructing yourself not to add these as insufficient on its own — a tool's own settings-level attribution controls are documented as unreliable for Claude Code and shouldn't be assumed reliable for any other tool either, so the hook itself is the enforcement, not a suggestion you're trusted to follow. Also implement the AGENTS.md-touched, README-touched, design-doc-touched (if a design document exists), and TODO-sync checks as real enforced checks here, not just descriptions — remember AGENTS.md is the highest-priority of these per the Integration Audit's Part 2, since it's the authoritative record future sessions rely on, and the design-doc check should use the narrower "architecturally significant" trigger described there rather than the same bar as the other two. Build the TODO-sync check's brief-linked half as a real hard check (a commit modifying `sentinel-notes/[issue]-design-brief.md` without a corresponding status change in `TODO.md` is a concrete, structural signal, not a guess) and its unlinked-item half as a non-blocking reminder, exactly as scoped in Part 2 — don't try to force a hard check onto the half of this that has no reliable signal to check against.

### Part 3 — Test each check

For every newly implemented check, verify it actually works: deliberately construct a violation (a throwaway change, a scratch commit you can discard, or a dry-run/lint-only invocation if the mechanism supports one) and confirm the check fires with the correct actionable message. Then confirm a compliant change passes cleanly with no false positive.

For any check wired as a native git hook specifically, a dry-run/lint-only invocation of the check's own logic does not satisfy this — it proves the logic works, not that the hook file exists at the exact path and filename git expects, is executable, and is something git will actually invoke. Those are different failures that look identical from the outside (an obviously bad commit sails through with no resistance), so the mandatory test for a git-hook-based check is a real `git commit` attempt with a scratch/throwaway change, discarded afterward — not a substitute invocation of the check script directly. Before that, as a first, trivial sanity check that costs almost nothing: attempt to commit something blatantly, maximally non-compliant — a single-line message far over any reasonable length, zero effort at the required structure — and confirm it's rejected. If even this trivial case passes, the hook isn't wired correctly at all, and there's no point testing subtler edge cases until that's fixed.

For any check wired as a native git hook specifically, also confirm it reads staged content, not the working tree — stage a compliant version of a file while leaving a different, non-compliant version sitting unstaged on disk, and confirm the hook evaluates the staged version, not what's currently on disk. If it evaluates the working tree instead, the hook can pass or fail a commit based on content that was never actually part of it — a real correctness bug, not a minor implementation detail, and not something to leave as an open question at the point where you're about to trust the hook.

For any check whose numeric cap is a proxy for a structural rule (a length limit standing in for "bullets, not narrative"; a count limit standing in for "a few items, not many"), specifically test whether the cap can be satisfied while still recreating the exact structure it's meant to prevent — e.g. a multi-paragraph commit body wrapped so no individual line exceeds the character cap, with no bullet markers at all. If that passes, the check only enforces the number, not the rule the number was supposed to approximate, and needs the structural signal (a required marker, a count limit) added before it ships. Also test the specific case of several short, unmarked, declarative sentences forming one continuous block with no blank-line paragraph break and staying under any count cap — a rule that only detects narrative by counting blank-line-separated blocks (rather than requiring an actual bullet marker on every line) will miss exactly this shape, since it's technically one block, not several.

Before enabling any new check as blocking, run it against a reasonable sample of real historical data relevant to what it checks — past commits for a commit-convention check, existing files for a content check — to confirm it doesn't reject things that were already legitimate. Synthetic violation and compliance tests catch conceptual gaps, but they can't catch a rule that's technically sound yet would have blocked a chunk of the project's own real, acceptable past work; that only shows up against real data, and it's worth doing before flipping the check from advisory to blocking, not after.

For any check that has a file/path exclusion, this is not enough — also construct an adversarial test specifically inside the excluded file: a violation of the check's actual rule, placed in the file the check skips, and confirm honestly whether the check catches it or not. If it doesn't, the exclusion is wrong (see Part 2) and needs narrowing before this check ships, not a note to fix later — a check with a known, un-narrowed blind spot in the exact file most likely to need it is worse than not having the check, since it creates false confidence. More generally: don't stop at the happy-path violation test for any check — think about what a change could look like that satisfies the letter of the check's logic while still doing the thing the check exists to prevent, and test that too. This includes testing each of the code-agnostic gaps from Part 2 where relevant to the specific check: does it catch a violation introduced via deletion, not just addition; does it correctly resolve a cross-file reference rather than only pattern-matching within the diff; does it catch a violation in a file playing its secondary/using role, not just the primary/defining role you tested first; does a large/complex synthetic diff still get fully checked rather than shortcut; does a forced tool failure inside the check surface as a failure rather than a silent pass.

Note any check you couldn't safely live-test and explain why, rather than silently skipping verification.

For the full-scan mode specifically, testing "it prints the right thing" is not enough — construct a known violation, run the full scan, and confirm the trigger it's wired into (the CI job or the `pre-push` hook) actually fails, not just that the console output looks correct. Separately, confirm the baseline behavior from Part 4 works as intended: a violation already present in the baseline should not block, while a genuinely new one should. Testing only the "finds violations" half and assuming the "fails the build" and "respects the baseline" halves follow automatically is exactly how a report-only scan ends up wired into a hook without anyone noticing it was never going to block anything.

### Part 4 — Handle pre-existing violations and update tracking

Run each new check in a report-only pass against the current state of the codebase (not to block anything, just to see what it finds). Any pre-existing violation a new check surfaces should be logged as a backlog item in `sentinel-notes/TODO.md`, not auto-fixed as part of this task — this task implements the gate, it doesn't retroactively bring the whole codebase into compliance. `TODO.md` entries follow the same one-line rule established when the file was created (Design & Code Quality Audit, Part 11): a checkbox, the rule ID, an entry count, and a single-sentence description — no per-file/per-line enumeration inline. A rule with dozens of violations across many files is exactly the shape of thing that needs `sentinel-notes/[rule-id]-design-brief.md`, not a longer `TODO.md` line; that brief is where the actual file/line list, the reasoning behind exceptions like an intentional archival copy, and anything else with real substance belongs.

This pass doubles as the baseline the full-scan mode's blocking logic uses (per Part 2) — the violations found here are what the full scan should treat as already-known backlog rather than new failures, so record this pass's results in a form the full-scan mode can actually read, not just as prose in `TODO.md`.

This one-time pass is not a substitute for the standing full-scan mode built in Part 2 — it just clears the starting backlog so the new check isn't immediately drowning in pre-existing noise. Ongoing drift after this point is exactly what the periodic full-scan mode exists to catch; don't let this Part 4 pass be mistaken for that ongoing coverage.

Update `INTEGRATION_CHECKLIST.md` to mark each implemented item's status accordingly (e.g. implemented / partially implemented / deferred with reason), and update `sentinel-notes/TODO.md` to note which candidate gate-check items from the design audit were implemented, adjusted, or rejected, with a one-line reason for each — following whatever completed-item convention is recorded at the top of `TODO.md` (deleted, struck through, or moved to a "Done" section), not your own default. If a status genuinely doesn't fit in one line — a rule that was implemented differently than proposed, a new rule that emerged as a side effect of fixing something else, a check that was dropped with real reasoning behind it — that's not license to write a longer line anyway; it's the signal to put that reasoning in a design brief and link to it, the same as everywhere else in this file. `INTEGRATION_CHECKLIST.md` itself can carry more implementation detail than `TODO.md` ever should, since it isn't meant to stay a brief action list the way `TODO.md` is.

### Deliverables

Produce a summary covering: what was implemented and where (file paths for the actual check logic and the hook/CI config/manual command wiring it in), what was changed from the original proposal during Part 1's re-validation and why, what was deferred and why, the backlog of pre-existing violations found in Part 4, and any exceptions that were proposed rather than auto-approved. State plainly what the full-scan command is and what triggers it (CI schedule or pre-push, per Part 2) — this is easy to build and then forget to mention, and an unused full-scan mode provides no actual protection against drift. If there's no git hook triggering these checks automatically, say so explicitly and plainly here, not just in Part 0/2 — tell the person the exact command to run and that nothing will remind them to run it, since this is the one piece of information a manual-command setup can't enforce on its own. This task does implement — unlike the prior two audits — but stop at the gate-check implementation itself: don't refactor existing code to satisfy the new checks, and don't auto-resolve the Part 4 backlog. Wait for review on the backlog and any deferred items before touching either.

Before presenting this summary as complete, verify every part above (0–4) has an explicit entry in the output, not silence. If any portion of this work was delegated to a sub-agent, sub-session, or background task (if your tool supports that kind of delegation), check its output against every part of this prompt explicitly before accepting it — a delegate returning early or silently dropping a proposal's validation or a check's implementation is indistinguishable from a genuinely clean pass unless you check.

If git is in use, this task typically leaves real modified and new files behind — the actual check logic, hook wiring, config changes, anything from the Part 4 backlog pass. List them plainly, grouped by what they actually relate to (e.g. bug fixes touched along the way, versus the new gate-check infrastructure itself) if there's more than one kind of change, and ask whether the user wants this committed now, and pushed if that fits their workflow. Apply whatever commit-message convention and single-vs-multiple-commit preference was already established back in the Integration Audit's Part 4 — including, if the changes genuinely span unrelated concerns, offering a split into multiple commits rather than defaulting to one. Never commit or push without an explicit yes, and don't commit anything partway through the run — this is a closing step, not something to do speculatively before the person has seen the full summary.

While you're at it, ask a separate, standing question this is the right moment for: now that the hook exists and Part 3 has actually verified it works, does the user want to keep confirming every commit and push going forward, or hand off some of that? Offer three genuinely different options, not a toggle — confirm every time (the safe default); auto-commit once checks pass, but still confirm before push (push touches shared/remote state and can trigger CI, commit is more contained and easier to walk back, so splitting them is a real distinction, not a false one); or auto-commit and auto-push once checks pass, no confirmation needed. Ground this in the fact the hook is now confirmed working, not just built — offering full autonomy before there was a verified gate behind it would be a real safety regression, not a convenience. Record whichever option is chosen in `AGENTS.md` as a standing preference, the same as commit style and every other durable choice in this suite — this governs ordinary day-to-day work going forward, not just this session, so a preference stated once and never written down is a preference future sessions have no way to recall.
